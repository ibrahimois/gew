# Multi-forge implementation plans

Generated by the `improve` skill on 2026-08-07 for the `next/multi-forge`
branch. These plans were written against identical v0.3.0 source snapshots at
GitHub commit `2f1a3fc6723ded372aa5f94cf863c6a66b08c866` and Gitea commit
`1a860b47b8b26597ca3c1ab91971c63b621e5baf`.

Execute Plan 001 first. Plans 002–005 may then proceed independently, although
shipping one provider at a time is safer than developing all four concurrently.
Execute Plan 006 only after Plans 001–005 are complete and the provider
contract has stabilized. Every executor must read its plan fully, honor its
STOP conditions, and update the status below.

## Direction findings

| # | Direction | User value | Coarse effort | Risk | Evidence |
|---|-----------|------------|---------------|------|----------|
| 1 | Extract a provider-neutral remote contract and keep Gitea as the reference adapter | Preserves the existing CLI and makes additional forges possible without duplicating staging and merge logic | L | HIGH | `main.go:31-65` stores Gitea-shaped profiles/state; `main.go:520-546`, `main.go:605-674`, and `merge.go:137-170` call a concrete Gitea client directly |
| 2 | Add GitHub through its Git database API | Supports GitHub and GitHub Enterprise without the Git executable while retaining one remote commit per queued commit | L | MED | `main.go:650-668` already translates a queued commit into atomic file operations; GitHub exposes blobs, trees, commits, and non-force ref updates over REST |
| 3 | Add GitLab through its batched Commits API | Supports GitLab.com and self-managed GitLab, including nested namespaces | M | MED-HIGH | GitLab accepts an `actions[]` batch, but does not expose a branch-wide compare-and-swap field equivalent to Azure's `oldObjectId` |
| 4 | Add Bitbucket Cloud through its Source API | Covers Atlassian-hosted repositories with a REST-only multi-file upload | L | HIGH | Bitbucket accepts multipart add/update/delete operations and a `parents` field, but stale-parent behavior and clone performance need live characterization |
| 5 | Add Azure DevOps through its Pushes API | Covers Azure Repos with explicit branch concurrency protection | L | MED | Azure accepts multi-file `changes[]` and an exact `oldObjectId` for the branch update |
| 6 | Add an opt-in hybrid `.git` workspace while retaining `.gew` as the REST bridge | Gives editors and Git-aware tools a standards-compliant local repository without introducing Git transport, and provides a safe migration path for existing workspaces | L | HIGH | `.git` can own local index/objects/commits, but provider-created commit IDs can differ from local OIDs, so `.gew` must retain mappings and crash recovery |

Effort is coarse: **M** is several focused days and **L** is a multi-day to
multi-week change including contract, fixture, and live-provider tests.

## Target capability matrix

| Provider | Snapshot strategy | Atomic remote commit | Branch-wide optimistic lock | Initial scope |
|----------|-------------------|----------------------|-----------------------------|---------------|
| Gitea | Repository ZIP + recursive tree | `POST /repos/{owner}/{repo}/contents` | Partial: head precheck plus per-file blob SHAs | Existing behavior |

## Dependency notes

- Plans 002–005 require Plan 001 because provider adapters must implement one
  contract and reuse one conformance suite.
- GitLab and Bitbucket must remain clone/pull-only until their concurrency tests
  prove that a stale client cannot silently overwrite a changed remote file.
- Provider-specific code must not import or reimplement staging, diff, merge, or
  local commit-queue logic.
- Plan 006 follows all provider adapters because the hybrid export journal and
  migration must be tested against the final `Forge` contract and every enabled
  provider's real commit-ID and concurrency behavior.
- Plan 006 does not reverse the earlier rejection of Git transport. Its `.git`
  repository is local-only; all remote I/O continues through REST adapters, and
  `.gew` remains the synchronization journal.

## Findings considered and rejected

- **Dynamic Go plugins in v0.4**: rejected. Go's plugin mechanism is
  platform-sensitive and conflicts with the project's single-static-binary
  deployment goal. Use compile-time registered adapters behind a stable
  interface. A subprocess/JSON-RPC plugin protocol can be reconsidered after
  at least three adapters reveal the genuinely stable contract.
- **Use `go-git` instead of REST adapters**: rejected for this roadmap because
  the product requirement includes environments where Git transport itself is
  unavailable, not merely the `git` executable.
- **Use GitHub's per-file Contents API for push**: rejected because one local
  multi-file commit would become several remote commits and partial failure
  would expose an intermediate repository state.
- **Support Bitbucket Data Center in the Bitbucket Cloud adapter**: rejected.
  Atlassian exposes different Cloud and Data Center APIs; pretending they are
  one provider would make capability checks unreliable.
- **Promise identical behavior before live conformance tests**: rejected.
  Mock tests validate encoding, but only sandbox repositories can establish
  stale-head, branch-protection, empty-repository, and ambiguous-response
  behavior for each forge.
